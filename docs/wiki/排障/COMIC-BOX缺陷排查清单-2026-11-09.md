## A. 本地 ComfyUI 视频模型（未提交改动）

### A1 [P1，已确认] 配置读取失败后保存会覆盖原有全部配置

- 位置：`src/runtime/creation/localComfyVideo.ts` 的 `load()` 与 `saveLocalComfyVideo()`。
- 现象：只要 `localStorage['comicBoxLocalComfyVideos']` 里有一条配置校验失败（例如手动改坏、以后校验规则变严、ID 重复），`load()` 就返回空数组，并提示「本地模型配置读取失败，原配置未覆盖」。此时用户在设置页新建并保存任意一个模型，`saveLocalComfyVideo()` 会基于空数组拼出 `[新配置]` 写回 `localStorage`，原有所有配置被覆盖。提示语与实际行为相反。
- 根因：读取失败时内存状态（空数组）和存储状态（原数据）不一致，保存逻辑却以内存状态为准整体写回。
- 修复方向（二选一，倾向第一种，改动最小）：
  1. 读取失败时设置一个「只读」标志，`saveLocalComfyVideo()` 在该标志为真时直接抛错，提示用户先处理原配置；或
  2. 逐条校验，只隐藏无效条目，保存时把原始无效条目原样保留写回。
- 验收：在 `src/runtime/creation/__tests__/localComfyVideo.test.ts` 新增测试——预置一条有效、一条无效的原始配置，模块加载后调用保存，断言原始存储中的条目没有丢失（或保存被拒绝）。先失败后通过。

### A2 [P2，待复现] 时长允许小数，可能写进整数输入

- 位置：`src/runtime/creation/creationModelRegistry.ts` 的 `getAllCreationModelSpecs()`（duration 字段 `step: 0.1`）；`localComfyVideo.ts` 的 `buildLocalComfyVideo()` 对 duration 只检查 `Number.isFinite`；设置页「最短/最长秒数」也是 `step="0.1"`。
- 现象：多数 ComfyUI 视频节点的时长或长度输入是 INT。用户选 4.5 秒时，工作流会带着 4.5 提交，ComfyUI 在校验阶段报错；用户只看到一个笼统的失败。
- 修复方向：以工作流里该输入的原值推断类型——原值是整数时，duration 字段 `step` 设为 1，`buildLocalComfyVideo()` 拒绝非整数；原值是小数时保持现状。不要新增配置项。
- 验收：单测覆盖「原值为整数时传 4.5 被拒绝、传 4 通过」和「原值为小数时 4.5 通过」。

### A3 [P3，已确认] 设置页小问题

- 位置：`src/components/settings/LocalComfyVideoSettings.vue`。
- `edit()` 清空了 `message`，但没有把 `failed` 复位；`importFile` 成功时也不复位。先保存失败再切换编辑对象，后续提示的颜色和 `role` 仍是错误态。修复：`edit()` 和导入成功时把 `failed` 设为 `false`。
- 没有删除已保存模型的入口，用户只能手动清 `localStorage`。是否补充删除功能请先与用户确认（AGENTS.md：不写未被要求的功能），本条只记录。

### A4 [P3，已确认] 模型规格查询每次重建

- 位置：`creationModelRegistry.ts` 的 `getCreationModelSpec()`、`listCreationModels()`。
- 现象：两者每次调用都执行 `getAllCreationModelSpecs()`，复制整个注册表数组，并为每个本地配置重新执行 `baseSpec()`。`getCreationModelSpec` 在面板的计算属性和任务存储里调用频繁，每次返回新对象，按引用比较或缓存的地方会失效。
- 修复方向：本地规格按 `localComfyVideos` 变化缓存（与 `useCreation.ts` 里已有的 `watch(localComfyVideos, ...)` 同步失效），查询函数复用缓存。
- 验收：已有 `useCreationPlanMaterialization`、`localComfyVideo` 测试保持通过；补一条断言「配置不变时两次查询返回同一对象，保存后返回新对象」。

- 位置：`src-tauri/resources/deepseek-harness/package-lock.json`，约 680 处 `resolved` 指向 `https://registry.npmmirror.com/...`。
- 现象：本次排查时镜像返回 `500 Internal Server Error ... [ER_NO_SUCH_TABLE] Table 'npmmirrordb.team_packages' doesn't exist`。`npm ci` 优先使用锁文件里的地址，即使换 registry 也会继续请求镜像，导致 `pnpm run build:deepseek-harness` 失败，并连带 B2、B3、B4 和 9 个 focused 测试失败。
- 修复方向：把锁文件中的 `resolved` 改回官方 `https://registry.npmjs.org/`（`integrity` 不变，内容哈希一致），镜像改由开发者本机 `.npmrc` 决定。可用 `npm ci --registry=https://registry.npmjs.org/` 验证锁文件仍可安装。不要改依赖版本。
- 验收：清空 `src-tauri/resources/deepseek-harness/node_modules` 后执行 `pnpm run build:deepseek-harness` 成功；`git diff` 只涉及 `resolved` 字段。

### B3 [P2，已确认] 测试并发运行 harness 准备脚本

- 位置：`scripts/__tests__/deepseek-permission.test.mjs:11`、`scripts/__tests__/wiki-native.test.mjs:48`、`scripts/__tests__/deepseek-harness-patch.test.mjs:19`，三处都直接执行 `scripts/prepare-deepseek-harness.mjs`；`scripts/run-focused-tests.mjs:293` 用 `node --test` 并发运行文件。
- 现象：harness 未就绪时，三个进程同时对同一目录执行 `npm ci`（它会先删除 `node_modules`），日志里出现 `ENOTEMPTY: directory not empty, rmdir ...\node_modules\@emnapi` 和 `TAR_ENTRY_ERROR`，安装结果残缺。即使镜像正常也可能失败。

- 验收：删除 harness `node_modules` 后执行 `pnpm run test:focused:run`，安装只发生一次，不再出现 `ENOTEMPTY`。

### B4 [P3，已确认] dist 清理测试与 harness 状态耦合

- 位置：`scripts/__tests__/memory-product-separation.test.mjs:190` 的用例「Desktop dist rejects Python caches and prunes them recursively」。
- 现象：用 `DESKTOP_DIST_DIR` 指向临时目录后，清理确实成功（`__pycache__` 已删除），但第二次审计返回 1，因为 `scripts/audit-desktop-dist.mjs` 还会检查仓库里的 `src-tauri/resources/deepseek-harness/node_modules/node/bin/node.exe`。被测逻辑正确，测试却因无关的环境状态失败。
- 修复方向：审计脚本在使用 `DESKTOP_DIST_DIR` 覆盖时，harness 运行时检查也应基于同一套可注入路径（或提供一个可覆盖的 harness 根目录环境变量），测试为其准备假文件。不要删除生产构建里的 harness 检查。
- 验收：harness 未安装时该用例通过；正常 `build:desktop` 在缺 harness 时依然报错。

### B5 [P1，已确认，长期遗留] Rust 测试进程无法启动

- 现象：`pnpm run test:tauri` 编译通过，运行 `jiucaihezi_app_lib-*.exe` 时退出码 `0xc0000139 (STATUS_ENTRYPOINT_NOT_FOUND)`。知识库自 2026-10-27 起多次记录此问题，见 [[排障/Windows桌面全局审查-2026-10-27]]、[[运维/COMIC-BOX仅Windows代码清理-2026-10-27]]。这意味着包括本次新增的 `comfy_files.rs` 路径隔离测试在内，全部 Rust 单测在默认流程里都没有执行；`test:focused` 也因此永远以失败结束。
- 根因（高度可能，需验证）：`tauri_build::build()` 只把 Windows 应用清单（启用 Common Controls v6）嵌入 bin 目标，lib 的测试 exe 没有清单，加载时找不到 `comctl32` v6 才有的入口（例如 `TaskDialogIndirect`）。这是 Tauri 在 Windows 上的已知问题。
- 修复方向：在 `src-tauri/build.rs` 中改用 `tauri_build::try_build(Attributes::new().windows_attributes(WindowsAttributes::new_without_app_manifest()))`，并通过 `cargo:rustc-link-arg=/MANIFEST:EMBED` 与 `/MANIFESTINPUT:<清单路径>` 对所有目标（包括测试）嵌入同一份清单。清单内容需与 Tauri 默认清单一致（Common Controls v6 依赖、DPI 设置），避免改变正式 `comic-box.exe` 的行为。2026-10-27 记录提到隔离宿主方案因缺少 Windows SDK `mt.exe` 失败；链接器参数方案不依赖 `mt.exe`。
- 验收：`pnpm run test:tauri` 实际运行并报告通过数量（10-18 的历史记录是 491 通过、2 忽略）；`tauri:dev` 启动的窗口外观和对话框不变。
